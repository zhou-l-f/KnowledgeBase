企业知识库 RAG — 检索与生成优化实验报告

度量驱动的检索优化过程 + 评测 harness（harness 思想）落地记录
项目：KnowledgeBase  ·  生成模型：deepseek-flash  ·  向量模型：bge-small-zh-v1.5  ·  重排模型：bge-reranker-base

1. 背景与目标

知识库问答（RAG）的检索与生成质量，靠"感觉"无法优化——改一个参数同时影响多项指标，且彼此掩盖。本阶段目标有二：

  1. 让检索优化可量化：每一步都能看到前后指标，不达标可回退，杜绝"感觉变好了"。
  2. 落地 harness 思想：先立度量（评测集 + 指标 + 报告），再做优化；优化结论全部可复现、可回溯。
核心原则：评测与线上共用同一条检索/生成代码路径。二者若不一致，优化分数就是"假优化"。

2.3 语料与测试集

评测语料经两轮扩充：由最初 2 库 9 条 → 5 库 201 条（公司规章 / 公司运维 / 财务报销 / 人事招聘 / 安全合规），并刻意埋入同主题密集近义干扰簇（年假 vs 婚假/产假、磁盘告警 vs CPU 告警、备份位置 vs 备份保留 vs 备份恢复、跨库的"请假"等）。测试集 70 条（67 正样本 + 3 负样本）。

扩语料的动因：首版 9 条 QA 时 k=4 几乎必然命中，指标全 1.000、毫无区分度。语料与题目难度不足时，harness 测不出任何优化的价值。

3. 检索层优化过程

3.1 阶段一：优化 1 —— bge query 指令前缀 被否决

假设：bge 官方推荐给查询加指令前缀，应能提升检索。做法：加开关做 A/B 对照。

配置命中率@1命中率@k召回率@kMRR
无前缀（同期基线，48 样本）0.9781.0001.0000.985
加 bge 指令前缀0.9781.0001.0000.985

结论：四项指标零变化，排名一条未变（MRR 精确相同）。原因：bge zh-v1.5 官方已说明指令前缀对中文 v1.5 影响不大（该建议主要针对 en-v1.5）。按证据回退，默认关闭，保留开关便于复验。

这正是 harness 的价值：一个"看起来该有用"的优化被数据证明无效，避免了盲改。

3.2 阶段二：优化 2 —— 两阶段检索 + 交叉编码器重排 已采纳

做法：向量召回 top-10 → bge-reranker-base 精排 → 取 top-k。此优化置于生产唯一入口 agent/service.py:retrieve()，评测直接度量其效果。

配置（200 条语料 / 70 样本）命中率@1命中率@k召回率@kMRR
k=4 无重排（基线）0.9851.0001.0000.990
k=2 无重排0.9850.9850.9850.985
k=1 无重排0.9850.9850.9850.985
k=4 重排1.0001.0001.0001.000
k=2 重排1.0001.0001.0001.000
k=1 重排1.0001.0001.0001.000

两个关键结论：

  1. 重排在每个 k 上都把唯一失分样本（年假一般能休几天？，正确答案被"婚假/产假"挤到第 3）修正到首位，命中率@1 +0.015、MRR +0.010。
  2. 小 k 才暴露真实收益：无重排时把 k 从 4 降到 1/2，召回率@k 从 1.000 掉到 0.985（正确项没进 top-1/2）；开重排后 k=1 即达 1.000。生产含义：每次喂给 LLM 的上下文可从 4 条砍到 1-2 条而准确率不降，省 token、降延迟、减少无关上下文干扰。
据此将默认 RETRIEVAL_K 由 4 调整为 2：上下文减半，同时保留一条冗余降低风险。

4.1 抓到的问题

问题一 · 测试集标注缺陷（正确性 0.993 → 1.000）
语料中存在复合问答 工牌或名片丢失了怎么办？，而测试问题只问"工牌"。模型只答工牌被误判 partial。修复：把该问答拆分为两条原子问答（问答对原子化是数据卫生要求），并调整判定规则不把参考答案中超范围的信息计入扣分。

问题二 · 过度断言（忠实度 partial，已被 prompt 约束修复）
年假能不能跨年使用？：资料只说"原则上当年休完、可申请延期"，模型却自行加了"不能跨年使用"。正确性判定为 correct（语义相符），忠实度判定为 partial（含未陈述断言）——这正是忠实度指标的价值：能抓出正确性漏掉的过度断言。加入 prompt 约束后，答案改为忠实复述原文，忠实度转 faithful。

4.2 重要方法论发现：LLM 判定存在波动

同配置复跑两次，忠实度出现 0.993 与 1.000 的差异；逐样本核对发现部分波动属于判定噪声（如 办公室能穿拖鞋吗？ 的答案完全有资料支持却被判 partial）。

判定波动（标准差）
±0.004
≈ 1 / 67 个样本
可信判定阈值
> 0.004
差值小于波动即不可信
降噪手段
--repeat 3
多轮取均值 + 波动量化

因此：任何小于波动幅度的指标差都不能当成优化收益；harness 的 --compare-with 已内置该判据，差值在噪声内会自动标注。

5.2 方法论沉淀

  • 单一入口：所有检索优化只改 retrieve()，评测与线上同源 → 杜绝"假优化"。
  • 报告自描述：每份报告记录配置 + 指标，--compare-with 出前后对比，全部可回溯。
  • 数据卫生即评测质量：问答对必须原子化，否则判定失真。
  • harness 会饱和：每次优化后须主动加难度（扩语料 / 加难题），否则指标失去分辨力。
  • 先降噪再读结论：差值须大于判定波动，否则只能记为"待复验"。

6. 后续优化方向

优先级方向理由
高引入独立判定模型波动与偏差的根源是"同源自评"，换独立 judge 可同时降偏差与波动
高harness 接入回归门禁已具备噪声判据，可在配置变更后自动跑分，指标下降超阈值即告警，防负优化
高扩难度后重启检索优化检索与生成层均已饱和，须加多跳 / 跨文档 / 术语缩写难题才能继续度量
中混合检索（BM25 + 向量）对 CPU、offer 等英文缩写与专有名词的召回更稳
中Query 改写 / 扩展用 LLM 改写查询以覆盖口语化问法
中拒答阈值化当前负样本靠 prompt 兜底，可加相似度阈值，避免"有文档就硬答"
低多模态（图片参与生成）媒体已支持存储与佐证展示，接入视觉模型后可用于生成

7. 运行方式

# 检索层：固化基线 / 新配置 / 前后对比
python -m eval.run_retrieval_eval --tag baseline
python -m eval.run_retrieval_eval --tag v2 --k 2 --note "..." --compare-with baseline

# 生成层：降噪评测（推荐 3 轮起）
python -m eval.run_answer_eval --tag answer_v1 --repeat 3
python -m eval.run_answer_eval --tag answer_v2 --repeat 3 --compare-with answer_v1

# 维护测试集：导出库中问答
python -m eval.dump_qa 公司规章
